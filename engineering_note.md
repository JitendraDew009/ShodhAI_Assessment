# Engineering note: workflow reviewer

## Scope and design

The submission provides one standard-library Python application, JSON contracts, synthetic fixtures, an offline CLI, regression tests, an optional model-client protocol, and machine-readable evaluation outputs. The implementation is deterministic; it does not depend on a paid model, GPU, network service, real ticket data, or model training. Python 3.13.17 was the execution environment; the declared range is 3.11–3.13.

The reviewer uses structured, anchored requirements rather than attempting to infer policy from arbitrary prose. Each source rule preserves an anchor and exact excerpt and is annotated with a condition AST, destination and precedence. Source order is authoritative unless all rules carry unique explicit precedence values. Versioned approval records are top-level authority only, scoped to the exact review revision, ordered by sequence then ID. Unapproved suggestions do not change effective requirements. Contradictions block instead of choosing a convenient approval.

IDs help evidence navigation but do not establish correctness. The source rule set acts as an ordered routing oracle. The specification is normalized by its explicit precedence or serialized order; the workflow is traversed from its start node; the Python subset is safely interpreted from AST. Each is compared to the oracle. A mismatch reports a concrete ticket, expected/actual route and relevant evidence. This catches omissions, precedence mistakes, branches, thresholds, missing-value behavior and linked-code drift even when metadata looks plausible.

The declared condition language includes missing/present, equality, membership, inclusive/exclusive numeric comparisons and nested AND/OR/NOT. Declared seconds/minutes/hours are normalized consistently. The Python subset is one `route(ticket)` function with conditionals, return strings, `ticket.get`/subscripts, Boolean operators and comparisons. It is parsed, never executed. Numeric values are partitioned at every boundary, next representable values, interior intervals and exterior representatives; categorical constants, missing and other values are included. Their Cartesian product is exhaustively checked up to 10,000 cases. Therefore equivalence is exhaustive for the supported comparison-only language and inferred types, not arbitrary prose, arithmetic, arbitrary Python or a larger unbounded domain. Unsupported, ambiguous and over-limit cases remain visible and abstain. A blocker wins over incomplete status, with unreviewed scope disclosed.

The CLI rejects oversized input rather than truncating it. Reports are not cached and include an input digest. The optional model prompt treats bundle text as untrusted; only the deterministic reviewer decides the outcome. A report must cite existing source rule IDs and exact artifact/version/location/excerpts. Calls, retries, limits and payload/response hashes are preserved. Fake-client results are solely interface/failure tests, not evidence of real-model performance.

## Evaluation

`evaluation/generate_cases.py` creates 21 deterministic bundles. `evaluation/labels.json` was authored separately and is never part of a reviewer bundle or prompt. Seventeen development cases and four held-out cases are frozen in `evaluation/frozen_checkpoint.json` before the final run. Labels cover nine valid cases (baseline, equivalent Boolean grouping, renamed IDs/reordered serialization, approved change, ignored suggestion, injected comment, equivalent seconds, NOT and membership formulations), nine defects (missing requirement, threshold drift, precedence overlap, wrong and missing workflow branches, inclusive/exclusive boundary, interacting decisions, approval conflict) and three incomplete cases (ambiguous source, unsupported Python and a fake timeout). The paired cases distinguish behavior changes from harmless serialization/ID changes. The independent expected routes are manually defined in the base bundle and labels; they are not generated by calling the reviewer.

Run the same frozen 21 bundles with:

```powershell
python evaluation\run_evaluation.py
```

The runner reports denominators, expected/actual counts, false passes, false blocks, incomplete counts by expected class and split, evidence/counterexample quality, runtime and model calls. The initial checkpoint checks source against the specification and explicitly leaves graph/code unreviewed. The final run adds exhaustive graph and safe-code equivalence. The controlled ablation disables only code behavioral equivalence and discloses the lost scope; no inputs or labels change. Results are saved in `reports\metrics.json` and `reports\evaluation.json`. All model metrics are fake-client only; no live-model result is claimed.

The final run classified 21/21 correctly: 9/9 valid PASS, 9/9 defective CHANGES_REQUIRED, and 3/3 expected INCOMPLETE. It had 0/9 false blocks on valid bundles, 0/9 false passes on defects, nine supported blocker findings, seven behavioral counterexamples, and no unsupported blocker. The four held-out labels were 4/4 correct. The frozen checkpoint mode classified 8/21 correctly (5 blockers, 16 incomplete, no passes); its narrow scope abstained on all nine valid cases and on four defects. This is a declared limited initial mode in the same frozen implementation, not a claim that a separate historical source snapshot was preserved.

With code-behavior equivalence ablated, 11/21 were correctly classified (8 blockers and 13 incomplete). All nine valid cases became INCOMPLETE because snippet review was disabled; the code-boundary defect also became INCOMPLETE rather than a blocker. Thus the ablation created no false pass/block but lost one localized defect and useful PASS decisions. Measured local CPU runtimes were about 0.010 s checkpoint, 0.112 s final and 0.017 s ablation. The fake timeout case used two calls (one retry) per mode; real-model calls were zero.

## Debugging examples

1. **Malformed-source path crashed.** The first suite run emitted `UnboundLocalError: cannot access local variable 'approval_conflict' where it is not associated with a value` on the ambiguous-source bundle. The parse error exited before assigning the conflict state, but report finalization still read it. The focused fix initialized the state before parsing; the unsupported-source case now returns `INCOMPLETE`. Regression: `test_frozen_cases_match_expected_labels` includes this case and checks the full expected status.

2. **The purported reorder variant changed behavior.** The first suite run reported `AssertionError: 'CHANGES_REQUIRED' != 'PASS'` for the case labeled as a harmless reorder. The fixture reversed a list whose order was the precedence contract, so its label was wrong. The contract now permits explicit unique `precedence`; the fixture reverses serialized records while retaining precedence and renames IDs, and a separate defective fixture swaps R2/R3 precedence. Regression: the frozen-cases test checks both outcomes. This was an evaluation-data bug, not a reviewer false negative.

The initial schema syntax check also caught a missing closing brace in the snippet schema; it was corrected, and `test_published_schemas_remain_parseable` now guards schema JSON parsing. The schema deliberately permits unsupported condition objects and absent branch fields as review inputs so the application can report them rather than discard them.

## Limitations and AI assistance

Source prose is preserved as evidence but must be annotated with the structured AST; free-form language is not proved. Ticket field types are inferred from supported comparisons rather than a full external ticket schema. Workflow cycles, unreachable nodes and oversized domains are not treated as verified. No live model was connected, and there is no claim of model semantic performance. JSON reports, fixture generator, expected labels and separate schemas allow inspection and rerun.

AI assistance was used to scaffold and iteratively debug the implementation. I verified the generated behavior with focused Python regression tests, schema parsing/validation, full frozen-case evaluation, and command-line execution; actual failures and fixes are recorded above. No private data or secrets were used.
